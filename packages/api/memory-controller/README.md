# @deepseek-ai/dsh-api-memory-controller

English | [中文](README.zh.md)

## Summary

The **memory controller** owns the Host-side `memory` Remote namespace. The bio-memory plugin is agent-facing and never publishes a view a browser could read; this package is that view. It projects the store into a graph — one node per memory, links joining memories that share a fact key or a scope — and exposes per-scope counts, aggregates, mount status, and the one write the Memory Settings page offers. Assembling the graph on the Host keeps the edge semantics in one pass over the store instead of shipping every memory to repeat the grouping.

<a id="use-this-package"></a>
## Use this package

Mount `@deepseek-ai/dsh-api-memory-controller` in a Host composition that may also mount `@deepseek-ai/dsh-memory`, and register its Remote contribution in the client Remote assembly. The namespace then answers `ctx.remote.memory.graph()`, `.status()`, `.forget()`, the three judge-model verbs, and the three pattern verbs.

### Reading the graph

`graph()` returns four fields. `nodes` is one projection per live memory: its id, content truncated for transport, kind, scope, lifecycle state, confidence, importance, usage count, observation and last-access times, forget score, fact key, and the two user flags. `edges` carries the links. `scopes` counts memories per scope. `stats` totals the set, breaks it down by lifecycle and kind, and reports how many memories are linked.

Two independent relations produce the edges, because either alone leaves a misleading picture. A **same-fact** link joins memories whose content normalizes to the same subject and predicate — the versions of one claim. A **same-scope** link joins memories stored under the same scope, which is what makes a project's memories read as one cluster. A memory with neither is a genuine isolate and carries no edge.

### Reading status and forgetting

`status()` reports whether the plugin is mounted, and when it is, the total and the newest observation time. The page uses it to choose between the graph and its "not enabled" state.

`forget()` takes a memory id and a mode. `delete` is governance: it is irreversible and records a tombstone, so the same fact cannot return from the same source. `suppress` and `deprecate` are lifecycle: they hide the memory reversibly and mark it stale. The split matches the agent-facing `memory_forget` tool, and both surfaces route through the same governance and lifecycle helpers, so the audit trail cannot tell which one asked.

### The judge model

The judgement layer runs a local GGUF model, and this namespace owns its delivery. `downloadModel()` starts a fetch from the pinned release and returns immediately, so a 278 MB transfer never blocks a Remote call; `modelDownloadStatus()` reports where it stands, and `idle` also means "checked and not there" so the page can show the finished state on a later run without offering a second fetch. `revealModelFile()` selects the model file in the platform's file manager, or opens the folder containing it where a manager offers no selection. Failure is not an error code: a failed download lands in the polled state as `status: 'failed'` with `error` set, because the page is the surface a user repairs it from and a thrown RemoteError would take that surface down with it.

### Patterns

`patterns()` lists every extracted pattern with its state, so the page can show candidates, active ones, and ones a person parked. `extractPatternsNow()` runs the offline extraction pass out of band — the button is what makes the panel useful before the scheduled run — and reports how many patterns it produced. `decidePattern()` is the approval write: `approve` makes a candidate active, `reject` archives it, `disable` parks an active one so re-extraction cannot revive it, and `enable` re-activates a parked one.

An unreviewed pattern never reaches the model through this surface or any other: every reader filters on `state === 'active'`, and a pattern becomes active only through `decidePattern()`.

<a id="understand-the-implementation"></a>
## Understand the implementation

<details>
<summary>Implementation internals — click to expand</summary>

The controller extends `TypertRemoteService` under the service key `memoryController` and the wire namespace `memory`. Its `./typert` and `./remote` exports are generated by the root build's Typert plugin from the `@Remote` decorators; nothing in `lib/typert.*.js` is hand-written.

### Reading through the plugin's service surface

Every verb reads through `memoryServices(ctx)`, the typed accessor the memory plugin publishes, rather than reaching into the store directly. When the plugin is not mounted that accessor returns `undefined`, and the controller answers `memory/unavailable` instead of throwing a type error — which is what lets the Settings page render an off state rather than an error.

### Edge construction

`buildEdges` groups the projected nodes twice. Fact groups become a clique, capped at the eight most recently observed versions: a key with hundreds of versions would otherwise be a complete graph, quadratic in edges for no visual gain. Scope groups become a star anchored on the most recently observed member, which keeps the edge count linear where a clique would be quadratic while still reading as one cluster. Edges are deduplicated by an order-independent key, so a pair linked by both relations appears once per relation rather than twice.

### Wire shape

`src/types.ts` is browser-safe: it declares the node, edge, scope-count, stats, status, and forget views, the judge-model download state, and the pattern view, decision request, and outcome, plus the `RemoteErrorDetailsMap` entries for `memory/unavailable` and `memory/not-found`. The download carries no error entry, because a failed download is a state rather than an error. The Remote client face the browser imports is generated from the same decorators, so the page reads the very declaration the Host answers.

<a id="model-experience"></a>
## Model Experience

None, as the package is an inspection-surface API owner that registers no prompt, tool, or session event; its `forget` write routes through the same governance and lifecycle helpers as the agent-facing `memory_forget` tool.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>


These limits define what this namespace exposes; they are current package constraints.

- **Content is truncated for transport** — each node's raw content is cut to 400 characters, so the graph and detail panel show a prefix of a long memory; the full content stays available to the agent through the recall tools.
- **The graph carries no cross-store relations** — the edges are derived from fact keys and scopes over live memories only; the repository's own `supports`, `contradicts`, and `supersedes` relation edges are not projected, so a relation recorded there does not appear as a link.
- **`graph()` reads the whole store** — the projection loads every memory on each call rather than paging, which is correct for a settings preview and would need a bound before it could back a live-updating view.

<a id="dev-note"></a>
### Dev Note

<details>
<summary>Working context for maintainers — click to expand</summary>

The controller must `export default MemoryController`. The Loader resolves a package as `exports.default ?? exports`, so a module with only named exports resolves to its namespace object, which has no `apply` and fails to mount. Every sibling controller (`settings-controller`, `workspace-controller`, `terminal-controller`) follows the same convention. This does not conflict with the rule that plugins export named `name`/`inject`/`Config`/`apply`: that rule governs the plugin shape, and a controller is a service class the Loader mounts directly.

</details>

**Runtime invariant:** No companion is published. A Host Remote owner that projects the memory plugin's store and routes its one write through the plugin's existing governance and lifecycle helpers; it emits no Cordis events and owns no cross-plugin mutable relation.
